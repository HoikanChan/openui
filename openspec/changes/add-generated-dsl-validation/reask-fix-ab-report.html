结论

本次改动的请求体和 prompt 注入已经生效：新 reask 请求全部从 temperature=0.7 降到 temperature=0，并且带上完整原始 system prompt、compact syntax rules、syntax repair hints 与组件签名。但从两轮修复率看，收益很小：reask 修复率从 12.5% 到 14.3%， 语法类从 0/10 到 1/12。

所以判断是：机制有效，效果不足 。这两步解决了“修复请求缺材料、温度太高”的确定性问题，但还不足以显著提升复杂语法失败的修复率。

分类表现

语法类 reask 是核心瓶颈。改动前两轮语法类为 0/10，改动后两轮为 1/12，仅出现一个成功样本： actual-target-gap。

  • 改动前：16 次 reask，2 次修复，10 次语法类全部失败。
  • 改动后：14 次 reask，2 次修复，12 次语法类修复 1 次。
  • 非语法类仍可修，说明签名/契约上下文对 unknown component、null-required 更有帮助。

为什么提升有限

  • maxAttempts 仍为 1。 用户本轮指定只做 prompt 和降温；复杂语法错误通常需要二次纠偏。
  • 语法错误往往不是单 token 修复。 多数失败同时出现 unresolved-ref、unclosed bracket、unexpected token，代表模型需要重写整段结构。
  • reask 只能补救被 gate 截断的后缀。 如果 accepted prefix 中已经埋了错误结构或抽象方式不好，后缀修复空间有限。
  • LLM 采样方差仍大。 同一 fixture 在不同轮次可能首轮直接 VALID，也可能走 reask 后失败。

建议下一步

  • 把 RepairPolicy.maxAttempts 从 1 提到 2，优先验证 tc-010、tc-015。
  • 对 syntax reask 增加“重写 invalid statement，不保留任何 JS 语法”的强约束，尤其是箭头函数、命名参数、`.includes`、函数声明。
  • 把 reask 输出再加一层轻量 lint prompt 或本地模板化 rewrite，专门处理命名参数转 positional 的高频错误。
  • 继续用两轮以上复跑，避免把首轮采样变好误判为 reask 能力提升。
